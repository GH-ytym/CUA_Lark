# CUA-Lark 技术开发文档

## 1. 项目概述

CUA-Lark 面向「飞书 AI 挑战赛：CUA-Lark · 让大模型像人一样操作飞书桌面端」设计，核心思路不是把所有操作都丢给视觉模型，而是先把问题拆成“可结构化执行的任务”和“必须视觉感知才能完成的任务”两类。前者优先交给 `Lark-CLI`，后者或 CLI 失败后的任务再交给 `CUA` 视觉执行器。这样做的价值非常明确：一是大幅提升执行确定性，二是降低视觉模型误操作的概率，三是让系统在比赛展示中既有“智能感”，又有“工程落地感”。

你们现在的构想从路线判断上是可行的，而且比“纯视觉点击流”更像一个真正可扩展的桌面智能体。因为飞书桌面端里的高频操作，例如发消息、建文档、改日程、更新表格、拉群、查链接，本质上都能被抽象为结构化动作。只要 CLI 能覆盖，系统就不需要每次看屏幕、理解布局、移动鼠标，这会让执行时间、错误率和可回放性都明显更优。视觉模型则只负责两个场景：第一，CLI 没有能力覆盖；第二，用户指令非常模糊，需要通过界面上下文辅助完成意图补全或目标确认。

因此，这不是“CLI 和 CUA 各写一套”的并列方案，而是“编排器驱动下的双执行器协同方案”。评委听到这里，一般会关注三点：为什么要先 CLI、CLI 失败后如何优雅降级、视觉执行如何保证安全。你们的方案对这三点都有回答空间，所以非常适合做比赛型展示。

## 2. 可行性判断

从工程实现角度看，这套方案完全可以在三人两周内做出可演示、可扩展、可答辩的版本，但前提是必须控制范围，不要追求“大而全”。最合理的目标不是“飞书所有功能都能操作”，而是“围绕 4 到 6 个高频业务场景，把链路打透”。建议你们把演示重点聚焦到以下几类：

- 聊天场景：发送消息、转发消息、定位某个会话。
- 文档场景：新建文档、填充模板片段、修改标题。
- 日历场景：创建会议、修改时间、补充参与人。
- 表格场景：定位单元格、更新一格或一行信息。
- 群协作场景：在群里同步执行结果、推送任务完成状态。

如果你们把这几个路径打通，系统就已经足够支撑“自然语言输入 -> Agent 判断 -> CLI 优先执行 -> 必要时 CUA 接管 -> 实时反馈”的完整闭环。比赛里真正加分的不是数量，而是稳定性、响应速度、失败恢复能力和解释能力。

最大的风险并不在 FastAPI 或 React，而在两处：一是 `意图到 CLI 命令` 的映射设计是否稳定；二是 `CUA 视觉执行` 是否会因为界面变化而脆弱。所以早期开发必须优先建立标准化中间层，不要让前端、后端、CLI 调用、视觉模型之间直接耦合。你们要让系统内部先形成统一任务结构，例如 `intent_type`、`entities`、`executor`、`status`、`fallback_reason`、`result_summary`，这样后面不管换模型、换 CLI、换演示场景，都不用推倒重来。

## 3. 建议补充的技术栈

你们当前已经选了 `FastAPI + Python + React + Lark-CLI + CUA 模型`，这条主线没有问题。但要把项目做成真正可开发、可调试、可演示的版本，还建议补充以下技术能力。

第一类是状态与事件能力。建议至少准备一个轻量状态层，开发期可以先用内存实现，演示增强版可切 Redis。因为你们的执行流程天然是多阶段状态机，不只是“发起请求、返回结果”这么简单。用户提交后会经历 `queued`、`parsing`、`cli_running`、`cli_failed`、`cua_running`、`completed`、`failed` 等状态，前端需要订阅这些状态，飞书侧也可能需要回推中间结果。没有状态层，整条链路会非常难调。

第二类是实时反馈能力。建议后端使用 `SSE` 作为前端进度流的基础协议，而不是一开始就上 WebSocket。因为你们目前是典型的单向进度推送模型，SSE 实现更轻、调试更简单、和 FastAPI 适配成熟。用户在飞书侧边栏里输入一句话后，看到“解析中”“CLI 执行中”“CLI 失败，切到视觉模式”“执行完成”这样的时间线反馈，会显著提升产品完成度。

第三类是可靠性能力。建议补充：

- `structlog` 或等价方案：做结构化日志。
- `tenacity`：做 CLI 与外部接口的重试控制。
- `redis`：后续用于任务状态和简单队列。
- `orjson`：优化响应序列化。
- `pytest + pytest-asyncio`：做关键流程测试。

第四类是模型与安全能力。视觉模型虽然是保底，但不能“想点哪就点哪”。至少需要设计以下约束：

- 最大动作步数限制。
- 高风险操作白名单或二次确认。
- 每步执行前后的截图留档。
- 失败时输出可解释原因，而不是沉默失败。

第五类是工程协作能力。建议统一使用：

- Python `3.12`
- Node.js `20+`
- `ruff` 作为 Python 规范工具
- TypeScript 严格模式
- `.env` 管理所有本地配置

## 4. 总体架构设计

系统建议采用分层架构，核心角色包括：前端侧边栏、FastAPI 接入层、任务编排层、意图解析层、执行器路由层、CLI 执行器、CUA 执行器、反馈与流式通知层。它们之间的职责应当明确分离。

前端只负责四件事：接收用户输入、展示任务进度、展示执行结果、展示失败原因。它不参与任何执行策略判断，也不直接知道 CLI 或 CUA 的具体细节。

FastAPI 接入层负责暴露统一 API，例如创建任务、订阅任务流、查询任务详情、健康检查等。接入层不直接写复杂业务逻辑，它只把请求转换为标准化内部对象。

任务编排层是系统大脑。它收到标准化任务后，先调意图解析服务；如果解析结果可映射到 CLI，就调用 CLI 执行器；如果不能映射，或者 CLI 执行失败且错误属于可降级类型，就切换到 CUA 执行器；最后再通过反馈服务统一回推结果。

意图解析层负责做两件事：一是识别用户目标类型，二是提取关键信息实体。例如“把明天下午 3 点的会议改到 4 点”，这里至少要抽出动作是 `reschedule_meeting`，目标对象是 `meeting`，原时间是 `tomorrow 15:00`，新时间是 `tomorrow 16:00`。这一步结果不能是松散文本，必须是结构化对象。

执行器路由层负责判定最佳执行路径。注意这里不是简单 if-else，而是基于能力表和运行结果决定。建议内部维护一张“能力矩阵”，标记哪些意图支持 CLI，哪些只能走 CUA，哪些需要人工确认。

CLI 执行器的职责是高确定性调用。它接收已结构化的动作对象，调用 Lark-CLI，拿到标准输出、退出码和错误信息，再统一转成内部结果对象。

CUA 执行器的职责是感知与动作。它需要读取当前界面信息、生成分步动作计划、执行鼠标键盘操作、在每步后验证结果，并在必要时终止或回滚。比赛版本不一定要真做完整回滚，但至少要做到“能停、能报错、能解释”。

反馈与流式通知层负责把任务状态广播给两个方向：前端侧边栏和飞书聊天会话。这样无论用户在侧边栏看，还是在群里等结果，都能获得一致反馈。

## 5. 核心执行流程

推荐的标准流程如下。

第一步，用户在飞书侧边栏输入自然语言。前端通过 `POST /api/agent/execute` 提交请求，请求中带上原始文本、会话上下文、用户身份以及当前容器类型。

第二步，后端生成 `task_id`，立刻返回，并开始后台编排。与此同时，前端通过 `GET /api/executions/{task_id}/stream` 订阅进度流。

第三步，编排器把状态切到 `parsing`，调用意图解析服务。若解析成功且存在 CLI 能力映射，则状态切到 `cli_running`。

第四步，CLI 执行成功，则直接写入结果，状态切到 `completed`。若失败，则判断是否允许降级。如果是超时、参数不完整、命令无映射、命令执行错误但目标场景可通过 GUI 完成，则状态切到 `cli_failed` 后再进入 `cua_running`。

第五步，CUA 执行器读取当前 GUI，上报“理解到了哪些界面元素”“接下来要执行哪些动作”。实际演示时，这里非常适合做时间线展示，因为它能体现智能体“像人一样操作”的过程感。

第六步，若 CUA 成功，则状态切到 `completed`；若 CUA 也失败，则状态切到 `failed`，并返回可读错误，例如“界面未找到目标会议卡片”“高风险操作触发安全保护”“视觉模型无法确认当前焦点窗口”。

第七步，反馈服务将最终结果推送到前端，并可选同步发回飞书聊天窗口，例如“已将会议从明天 15:00 调整到 16:00”。如果失败，也应该返回清晰的失败说明与建议动作。

## 6. 项目结构设计

当前仓库建议维持 monorepo 结构，理由是比赛周期短、前后端联调频繁、脚本和文档需要统一管理。推荐结构如下：

```text
FSAgent/
├─ backend/
│  ├─ app/
│  │  ├─ api/
│  │  ├─ core/
│  │  ├─ domain/
│  │  ├─ executors/
│  │  ├─ integrations/
│  │  ├─ schemas/
│  │  └─ services/
│  └─ tests/
├─ frontend/
│  └─ src/
│     ├─ app/
│     ├─ pages/
│     ├─ components/
│     ├─ features/
│     ├─ lib/
│     └─ types/
├─ docs/
├─ scripts/
├─ .env.example
└─ README.md
```

后端目录的职责建议如下：

- `api`：路由定义与 HTTP 接入。
- `core`：配置、日志、依赖注入。
- `domain`：状态机、实体、上下文。
- `executors`：CLI 与 CUA 两类执行器。
- `integrations`：飞书接口、CLI 适配器、视觉模型客户端。
- `schemas`：请求响应模型。
- `services`：编排、反馈、会话、流处理等应用逻辑。

前端目录的职责建议如下：

- `app`：应用壳和全局容器。
- `pages`：页面级组装。
- `components`：通用展示组件。
- `features`：与执行流强相关的业务 Hook。
- `lib`：API 客户端与工具封装。
- `types`：前端共享类型。

目前源码文件保持“每文件一行注释占位”，这是合理的，因为你们此阶段更需要先统一边界和职责，而不是抢着写实现。只要结构清晰，三个人就能并行推进而不互相阻塞。

## 7. 接口与数据模型建议

建议第一阶段先做以下 API。

`POST /api/agent/execute`

- 输入：`message`、`session_id`、`user_id`、`conversation_type`、`context_hint`
- 输出：`task_id`、`accepted_at`、`initial_status`

`GET /api/executions/{task_id}`

- 输入：`task_id`
- 输出：任务当前状态、执行器、结果摘要、错误信息、时间戳

`GET /api/executions/{task_id}/stream`

- 以 SSE 形式持续输出任务事件
- 事件体建议包含：`event_id`、`task_id`、`status`、`message`、`payload`、`created_at`

`GET /api/health`

- 输出：服务存活状态、版本号、可选依赖状态

核心领域模型建议包括：

- `TaskContext`：保存请求链路中的上下文元数据。
- `ParsedIntent`：保存意图类型、实体、置信度、歧义标志。
- `ExecutionDecision`：保存是否走 CLI、是否可降级、降级条件。
- `ExecutionEvent`：保存状态更新和时间线消息。
- `ExecutionResult`：保存最终结果摘要、执行器、证据与错误信息。

你们后面不管接哪家模型、用哪种 CLI 包装方式，只要都遵守这几个对象，系统就不会散。

## 8. 三人两周任务分工

三人团队最怕的不是工作量不够，而是边界不清和联调太晚。建议按“后端编排 / 执行集成 / 前端体验”三条主线拆分，每个人都有主责，也都有少量交叉接口。

### 成员 A：后端编排负责人

主责：

- FastAPI 项目骨架与 API 设计
- 任务状态机与领域模型
- 意图解析服务接口
- SSE 进度流与统一返回结构
- 日志、配置、错误码设计

交付目标：

- 能创建任务并返回 `task_id`
- 能持续推送状态变化
- 能把 CLI 与 CUA 的结果统一包装

### 成员 B：执行层负责人

主责：

- Lark-CLI 适配器
- CLI 能力矩阵与命令映射
- CUA 视觉执行器接入
- 降级策略与失败分类
- 执行截图、日志证据留存

交付目标：

- 至少打通 3 个 CLI 场景
- 至少打通 1 到 2 个 CUA 保底场景
- 能在 CLI 失败后自动切换到视觉执行

### 成员 C：前端与演示负责人

主责：

- React 侧边栏 UI
- 输入框、时间线、结果卡片
- SSE 订阅与状态可视化
- 飞书 AppLink 容器适配
- 演示脚本、交互细节、录屏准备

交付目标：

- 前端能流式展示任务阶段
- 能突出“CLI 优先、CUA 接管”的切换过程
- 演示时观感清晰、状态可解释

### 交叉协作规则

- 每晚固定一次 15 分钟站会，只同步阻塞点。
- 所有对外字段先写入文档，不允许口头约定。
- 第 4 天前必须完成第一次前后端联调。
- 第 8 天前必须完成 CLI -> CUA 降级链路联调。

## 9. 两周里程碑计划

### 第 1 周

第 1 天到第 2 天：完成项目骨架、配置规范、任务对象、前端基础布局、CLI 能力清单。

第 3 天到第 4 天：完成执行 API、SSE 进度流、前端时间线、至少 1 个 CLI 场景通路。

第 5 天到第 7 天：扩展到 3 个 CLI 场景，并沉淀错误分类与降级条件；同时接入视觉模型最小可用链路。

### 第 2 周

第 8 天到第 10 天：打通 CLI 失败后自动走 CUA 的完整闭环，补齐截图、日志和前端状态说明。

第 11 天到第 12 天：围绕比赛 Demo 打磨 2 到 3 条黄金路径，减少随机性，提高演示稳定性。

第 13 天：做全链路压测和异常演练，例如 CLI 超时、GUI 焦点丢失、网络慢、模型返回不稳定。

第 14 天：录制演示、整理答辩材料、准备技术亮点与风险控制说明。

## 10. 环境配置与启动方式

本项目建议统一在 Windows 环境开发，这样更贴近飞书桌面端实际运行环境。当前仓库已经准备了环境脚本和 `.env.example`，推荐配置如下：

- Python `3.12`
- Node.js `20+`
- npm 最新稳定版
- 可选 Redis，本地没有也可先用内存模式
- 已安装并可执行的 `Lark-CLI`
- 一个可调用的视觉多模态模型服务

推荐启动流程：

1. 执行 `scripts/setup.ps1`
2. 根据 `.env.example` 填写 `.env`
3. 启动后端 `uvicorn`
4. 启动前端 `vite`
5. 通过飞书 AppLink 或浏览器本地联调页面验证交互

环境变量建议重点维护以下几类：

- 飞书应用配置：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_APP_LINK_TOKEN`
- CLI 配置：`LARK_CLI_PATH`、`LARK_CLI_TIMEOUT_SECONDS`
- CUA 配置：`CUA_MODEL_PROVIDER`、`CUA_MODEL_NAME`、`CUA_MODEL_API_KEY`
- 运行时配置：`REDIS_URL`、`EVENT_BACKEND`、`FRONTEND_ORIGIN`

## 11. 风险点与规避策略

第一，意图抽取不稳定。规避方式是先用“场景白名单 + 意图模板”控制范围，而不是追求开放式理解。比赛阶段宁可少一点，也要稳一点。

第二，CLI 映射不完整。规避方式是先做能力矩阵，把演示所需命令全部列出来，对每个命令标注参数要求、依赖前置和失败后的降级策略。

第三，视觉执行误操作。规避方式是加动作步数上限、目标确认提示、执行前后截图和高风险操作拦截。

第四，前端看不出系统亮点。规避方式是把“解析中”“CLI 优先命中”“CLI 失败原因”“CUA 接管中”“最终结果”显式展示出来，让评委看见系统做了什么判断，而不是只看见一个结果。

第五，时间不够。规避方式是把所有任务分成“必须完成”“有余力再做”两层。必须完成的是：统一任务对象、3 个 CLI 场景、1 个 CUA 场景、实时状态流、飞书侧结果回显。其余如多轮上下文记忆、复杂回滚、通用 GUI agent，都可以放到展示后的扩展规划里。

## 12. Demo 设计建议

比赛 Demo 建议不要只演示成功路径，而要刻意展示一次“CLI 失败 -> CUA 接管 -> 成功完成”的场景。因为这正是你们方案相较普通 Agent 的辨识度所在。

建议准备三条标准演示脚本：

第一条，纯 CLI 成功路径。例如“给产品群发一条提醒，说明今天 6 点前提交周报”。这条路径突出高确定性和快。

第二条，CLI 失败后 CUA 接管路径。例如“把明天下午 3 点的会议改到 4 点”，如果 CLI 在当前能力矩阵中不支持某种筛选条件或返回失败，就自动进入视觉执行。这条路径突出融合架构。

第三条，模糊意图补全路径。例如“把刚才那个表更新一下”，系统先提示需要补足目标信息，或读取当前上下文后给出候选确认。这条路径突出 Agent 的智能性和安全意识。

演示中一定要让前端时间线动起来，因为这能极大提升系统可信度。评委不会只看结果，他们会看系统有没有判断、有没有解释、有没有错误恢复。

## 13. 本阶段验收标准

到本阶段结束时，建议以以下标准判断是否可提交或可进入下一轮开发：

- 项目结构清晰，三名成员能各自独立推进。
- 环境脚本可用，新成员拉仓后能完成安装。
- 后端能创建任务并输出标准状态流。
- 前端能展示完整执行时间线。
- 至少 3 个 CLI 场景稳定可演示。
- 至少 1 个 CUA 保底场景稳定可演示。
- 失败时能给出可读错误，而不是无响应。
- 文档可支撑答辩，不需要靠口头临场解释系统结构。

## 14. 结论

总结来说，你们的构想不仅可行，而且是非常适合比赛的方案，因为它同时满足了三个关键要求：工程稳定性、智能体表现力、可解释的执行闭环。真正的重点不是把模型堆得多强，而是把“优先精确执行，必要时再视觉降级”的机制做扎实。只要你们把项目收敛在少量高频场景上，按本文的分工和节奏推进，两周内做出一个完成度很高的挑战赛作品是现实可达的。

下一阶段建议是：先锁定演示场景与 CLI 能力矩阵，再补 FastAPI 接口和前端时间线，然后尽快把第一条 CLI 成功链路与第一条 CUA 接管链路跑通。一旦这两条链路稳定，项目基本盘就立住了。

## 15. 项目管理落地文件

为确保技术方案与执行排期一致，项目管理层建议固定使用以下文件：

- `ABC-14day-plan.md`：三名成员 14 天逐日排期，包含主任务、当日验收、备任务。
- `docs/daily-ops-template.md`：每日站会模板、风险看板、验收清单模板。

使用建议如下：

1. 每天开工前，先在 `ABC-14day-plan.md` 勾当天主任务与当日验收标准。
2. 每日站会后，在 `docs/daily-ops-template.md` 记录阻塞项、风险等级和责任人。
3. 每天收工前，按验收清单确认“已完成、未完成、顺延原因”，避免任务漂移。

三人协作方式建议采用“先统一框架，再并行开发”，不建议三个人各自独立搭文件结构。原因是：

- 统一骨架可避免接口字段、目录规范、命名方式产生分叉。
- 并行开发阶段只需要围绕既定边界填充实现，联调成本显著更低。
- 比赛周期只有两周，减少重构和迁移比“前期各自探索”更重要。
